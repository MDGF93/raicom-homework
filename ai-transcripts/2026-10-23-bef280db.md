### Claude

It's OK as it is. Production code writes `'PARTNER'` in only one place: the `partner()` helper at [router.ts:225](src/router.ts:225). That helper already acts as the single source.

The other hits do not need a constant:

- **Tests** ([router.test.ts](src/router.test.ts), [golden.test.ts](src/golden.test.ts)): test literals are correct here. They lock the output contract. If they import the same constant as the code, a rename of the constant does not make a test fail.
- **Docs and output files** (`routes*.txt`, `ANSWERS.md`, `README.md`): `PARTNER` is printed output there, not code.

An enum would add code and remove no real risk. A typo in a test makes that test fail, so you would see it.

When to change it: if a second production location must produce or check `'PARTNER'` (for example, a summary that counts partner orders), export `const PARTNER = 'PARTNER'` from `router.ts` and use it in both places. You could also type `destination` as `'PARTNER' | \`WH-${string}\``, so that tsc catches a typo in a `===` comparison. Today, nothing needs either change.

I did not check whether the warehouse codes (`'WH-NJ'` and the others) also need a type. They come from the data files, so they are a different case.

### Claude

Warehouse codes don't need a type, but I found a gap in how they're checked.

**Why no type:** the codes come from three places at runtime: `warehouses.json`, the keys in `zones.json`, and the `--off` argument. `loadData` uses `as T` casts, so a type such as `'WH-NJ' | 'WH-GA' | …` would only claim the codes are valid. It wouldn't prove it. The real protection is the runtime check:

- [router.ts:65](src/router.ts:65) stops if a warehouse code is not in `PRIORITY`.
- [router.ts:66](src/router.ts:66) stops if the same code appears twice.
- [router.ts:76](src/router.ts:76) stops if an `--off` code is not a known warehouse.

The only code literals in production code are the `PRIORITY` list at [router.ts:28](src/router.ts:28). That list already is the single source of truth.

**The gap:** nothing checks the keys of `zones.json`. Suppose a key has a typo, for example `"WH-nj"`:

- [router.ts:182](src/router.ts:182) looks up `zones['WH-NJ']`, gets `undefined`, and skips WH-NJ for every order. There is no error.
- [router.ts:235](src/router.ts:235) still finds the ZIP prefix in the misspelled table, so the order doesn't stop at "not in zones".
- The result is wrong routes without any error. Orders that only WH-NJ can take go to PARTNER with "no warehouse can take it".

The fix is one loop in `validate`: every key in `zones.json` that holds a table must be a warehouse code. The `_note` key holds no table, so the check skips it. A second line could also require every warehouse to have a zones table.

I didn't check whether a warehouse with no zones table is ever valid. If it can be valid, add only the first check.
