### Claude

Your version works. It compiles, because the excess-property check only applies to fresh object literals. The result of `mk(...)` is not a fresh literal when it reaches `route(...)`, so the extra `products` passes.

I kept `: Data` for two reasons:

- **It ties the fixture to the real type.** If `Data` changes, for example a new required field, `mk` fails at its own definition. With your hand-written shape, `mk` keeps its old shape and the error moves to every `route(mk(...))` call.
- **It avoids a second copy of the type.** Your annotation repeats `Data` by hand, and `products` is a field the router never reads.

If you want `products` in the fixture because the real `catalog.json` has it, add `products` to `Data` in `router.ts`. Then `: Data` accepts it and you keep both benefits.

### Claude

Annotating `mk` with `: Data` is the better decision. Four reasons:

- **One source of truth.** `Data` in `router.ts` defines what `route()` accepts. A hand-written shape in the test is a second definition that can drift from the first.
- **Changes show up at the right place.** If the router starts to read `catalog.products`, you add it to `Data`. Then `mk` fails to compile until the fixture supplies it. That is the signal you want.
- **`Data` lists only what the router reads.** The real `catalog.json` has both `products` and `bundles`, but the router uses only `bundles`. A type that lists only the fields the consumer reads is good practice. It keeps the router independent of the rest of the file.
- **The fixture stays minimal.** A test helper should build the smallest valid input. A `products: []` that nothing reads adds noise and suggests the router depends on it.

Your version has one real advantage. It states the full file shape, so a reader sees what `catalog.json` contains. For that purpose, add `products` to `Data` when the router needs it, or document the file shape in one place, not in the tests.

One gap remains in `loadData`. `JSON.parse` returns `any`, so TypeScript does not check that the files match `Data`. Add runtime validation there if the input can come from outside your control. For this homework, I would skip it.
